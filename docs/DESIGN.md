# 設計ドキュメント

> 公開用の設計書。確定した設計のみ記載する。

## 1. 目的

「画像 + 期待項目リスト → 各項目の有無を判定」というタスクを題材に、

汎用 VLM でこのタスクを解くシステムを想定し、そのプロバイダ抽象は専用検出器(YOLO)への差し替えを許容する。本作はその「差し替える価値があるか」という意思決定を、公開データ(COCO val2017)で再現した検証台で答える。

1. **汎用 VLM に専用検出器(YOLO)を差し込む価値があるか**を、同一タスク・同一評価セットで統計的に定量化する(DS / CV)
2. 精度・コスト・レイテンシのトレードオフと、各モデルが失敗する条件を明らかにし、差し替え判断の条件に落とす
3. その評価をプロンプト・モデルの変更ごとに回す回帰ゲートを無料で運用する(LLMOps)

## 2. タスク定義

入力: 画像 1 枚 + カテゴリのチェックリスト → 出力: 各項目の有無。
正解は COCO val2017 のアノテーションから機械的に決定する(アノテーションコスト 0)。
チェックリストの全カテゴリは COCO 80 クラスに収まるため、COCO 学習済み YOLO がそのまま比較対象になる。

### 比較を「画像レベルの有無判定」に揃える設計判断

YOLO の素の出力は bbox 検出だが、フル IoU で比較すると「座標精度の勝負」に引っ張られ、(1) YOLO の native 出力に有利で VLM を不当に不利にし、(2) bbox マッチング(IoU・割当)で評価パイプラインが複雑化して統計・誤り分析という主眼がぶれる。そこで**主軸は画像レベルのカテゴリ有無**に揃える。

- YOLO の検出を「そのカテゴリを信頼度しきい値以上で 1 個でも検出したか」で `present` / `absent` に還元する。
- VLM は `present` / `absent` / `uncertain` を返す。
- 両者を同じ統計機構で突き合わせる。

ただし「VLM は座標・検出が弱い」という通説は必ずしも自明でない(密で雑然としたシーンでは recall が律速になりうる)。これを仮定で切り捨てず、**個数 recall を副軸**として検証する: 各カテゴリで「存在するインスタンスのうち何個を検出できたか(present 個数 / GT 個数)」を測る。フル IoU の座標照合はしない(上記の不公平・複雑さを避ける)ため、座標勝負には踏み込まずに「密シーン・小物体での取りこぼし」だけを取り込む。

YOLO は `uncertain` を持たない 2 値判定とし、「VLM だけが不確実性を表現できる」点自体を比較の観察対象として扱う(REPORT に記載)。信頼度しきい値付近を `uncertain` にマップする案は採らない。

## 3. 評価セット設計

- COCO val2017 から N=300 を層化サンプリング(物体数・最小 bbox 面積比で層化)。VLM API ラン 1 本で完結する規模
- 各画像に positive + negative カテゴリを 5〜10 項目。negative には混同しやすいカテゴリ(dog↔cat 等、`conf/eval.yaml` の confusable_pairs)を優先混入
- 難易度メタデータ(bbox 面積比、iscrowd、項目数)を付与し誤り分析に使う
- シード固定・JSON 確定保存。smoke セット(n=50)はフルの部分集合(CI 用)

## 4. 統計的評価

**主軸(有無判定)**

- per-category / macro / micro の P・R・F1(positive クラス = present)。3 値(VLM)は strict(uncertain を誤り扱い)と excl(uncertain を除外 + カバレッジ併記)の 2 通りで報告。YOLO は 2 値
- 観測単位は「1判定項目=(画像,カテゴリ)」だが、同一画像内の項目(5〜10件)は独立でない
  (画像300枚に対し項目2281件)。**全ての検定・推定でリサンプル/クラスタ単位を画像に揃える**
- 画像単位ブートストラップ 95% CI(n=10,000、percentile法)。YOLO/VLM それぞれの周辺CIに加え、
  **同一リサンプル添字を使ったペア差(VLM−YOLO)のCIを主推論とする**
  (2つの周辺CIの重複は差が非有意であることを含意しないため)
- YOLO vs VLM の対応あり検定として McNemar(項目単位)をクロスチェックとして併記する。
  主推論は画像単位ペア差ブートストラップCIとし、McNemarは補助的な位置づけとする
  (item accuracy の差のブートストラップは代数的にクラスタ対応版 McNemar と同値: diff=(n10−n01)/N)
- 誤り分析: taxonomy + ロジスティック回帰(誤答 ~ bbox 面積比 + 項目数 + crowd + gt_present)。
  説明変数に画像レベル定数(bbox面積比・項目数・crowd)を含むため、
  **クラスタ頑健標準誤差(`cov_type="cluster"`, groups=image_id)** で標準誤差・p値を計算する
- トレードオフ: 精度 / コスト / レイテンシのパレート(YOLO ローカル無料 vs VLM API 課金)

**副軸(個数 recall)**

- 各カテゴリで「存在するインスタンスのうち検出できた個数の比」を YOLO / VLM で算出。フル IoU はしない(§2)。密シーン・小物体での取りこぼしを定量化する

**運用観点の分析(コア)**

- **チェックリスト事前情報による過剰主張の測定**: チェックリストに項目を載せること自体が VLM の偽陽性(absent を present と誤る)をどれだけ押し上げるかを ablation で測る。部分施工の現場で起きやすい「期待しているのに無い部品を"在る"と誤る FP」を公開データで再現する。YOLO はこの事前情報バイアスを構造的に持たないため、対比が鮮明
- **risk-coverage 評価**: macro-F1 に加え、「uncertain / 低信頼を人間に回す → 危険誤り率を ≒0 に抑えたときに残るカバレッジ」の曲線を引く。運用指標(危険誤り率 / カバレッジ)を統計化したもの

> ストレッチ(M4 余力): 解像度 / タイル分割 × recall のトレードオフ(縮小で小物体 recall が落ちるか、タイル分割のコスト対効果)。高解像度・タイル分割が小物体 recall に効くか(recall を上げる一方でトークンコストが増える)を公開データで検証し、YOLO の固定入力解像度とも比較する。副軸(個数 recall)が前提

## 5. 再現性(MLflow / DVC を使わない)

- 各ランは `results/{run_id}.json` に確定保存(モデル版・評価セットの sha256・実行日時を記録)
- VLM レスポンスは (model, prompt, image, checklist) のハッシュをキーに `cache/` へ保存。ヒット時は API を呼ばない
- 評価セットはシード固定。これで MLflow/DVC 無しでも「同じ入力 → 同じ結果」を再現できる

## 6. 継続評価パイプライン

```
プロンプト/設定の変更(PR) → CI が mock の smoke セットで自動評価 → ベースライン比較
  → 回帰ゲート(macro-F1 の劣化幅で fail) → マージ
```

- プロンプト = コード: `conf/` で版管理し、変更は必ず PR 経由
- 回帰ゲート: macro-F1(strict) の劣化幅が閾値超で fail。mock プロバイダで回すため API 費ゼロ。McNemar p 値は参考出力(smoke n=50 では検定力不足のため、fail 判定には幅を使う)
- コストガード: 月間累積コストが上限超過で full eval をスキップ
- 運用モード: 週次 cron は廃止し `workflow_dispatch`(手動)のみ。維持費ゼロ

## 7. マイルストーン

1. M1: 評価セット構築 + 指標 / ゲートの実装 + mock で E2E 疎通・単体テスト(API 費ゼロ)
2. M2: YOLO プロバイダ実装 + YOLO 単独で全指標を算出(ローカル推論・API 費ゼロ)
3. M3: Gemini Flash プロバイダ実装 + ベースライン VLM ラン(N=300 を 1 回。ここで初めて API 費が発生)
4. M4: YOLO vs VLM 比較分析(McNemar + ブートストラップ CI + 誤り要因回帰 + パレート + 個数 recall + 過剰主張 ablation + risk-coverage。余力で解像度 / タイル)
5. M5: CI(回帰ゲートを mock smoke で無料運用)+ README / REPORT 仕上げ

無料で動く部分(M1 評価セット・指標・mock、M2 YOLO)を先に完成させ、課金を伴う VLM ラン(M3)は土台が固まってから 1 回だけ実行する。
